# Visual Servoing 설계 (D)

- 담당: D (윤다은), 브랜치 `feat/visual-servoing`
- 상태: 1주차 초안
- 기준: 회의록 역할 정의, `docs/interfaces.md` v0.7 (PR #1)
- 공통 인터페이스는 `interfaces.md`가 기준이다.

## 1. 범위

Nav2 정차 후 남은 위치 오차를 카메라 피드백으로 보정해, 물체를 팔이 잡을 수 있는 위치에 둔다.

```
Nav2 정차 → 관측 자세 고정 → Align (D) → IK 확인 (B) → Grasp (B)
                                  ↑              │
                                  └─ IK 실패 시 재정렬 ┘
```

- 제어 대상: **모바일 베이스** (`vx`, `wz`). 로봇팔은 정렬 중 움직이지 않는다.
- 팔 접근과 파지는 B 담당이다.
- MoveIt Servo는 팔 제어용이므로 사용하지 않는다.

## 2. 제어 방식

직접 제작하는 차체는 차동구동이라 옆으로 이동할 수 없다. 따라서 x/y 오차 대신 **거리 오차와 방위 오차**를 제어한다. 제어 입력(`vx`, `wz`) 2개로 오차 2개를 줄일 수 있다.

오차 기준 좌표계는 `base_link`다. `standoff`는 `base_link` 원점에서 물체까지의 xy 평면 거리다. `mm_description` 차체에서 `base_link` 원점은 두 바퀴 축의 중앙이라 차체 회전 중심과 같다.

### 2.1 오차 계산

1. 검출 결과에서 물체 픽셀 좌표 `(u, v)`를 얻는다.
2. 깊이 이미지의 bbox 중심 주변 값 중앙값을 `Z`로 쓴다. NaN/inf는 제외한다.
3. 카메라 좌표로 변환한다. `fx, fy, cx, cy`는 `/camera/camera_info` 값이다.

   ```
   X = (u - cx) * Z / fx
   Y = (v - cy) * Z / fy
   ```

4. 측정 시각(`header.stamp`)의 TF로 `base_link` 좌표 `(x_b, y_b)`로 변환한다.
   깊이는 bbox 중심 픽셀이 닿은 물체 표면까지 거리다. 물체를 세워진 원기둥(클래스별 반지름·높이, `object_shapes`)으로 보고, 중심축이 어디 있어야 bbox 중심 광선이 잰 점에 닿는지 반복 계산해 중심축 위치를 구한다 (5.2, 5.3). 옆에서 보면 반지름만큼, 위에서 보면 거의 0만큼 옮겨진다.
   같은 클래스가 여러 개면 첫 프레임은 `base_link` 방위가 가장 작은 검출, 이후는 직전 박스에 가장 가까운 검출을 따라간다 (5.3).
5. 오차를 계산한다.

   ```
   e_r = sqrt(x_b^2 + y_b^2) - standoff
   e_b = atan2(y_b, x_b)
   ```

### 2.2 제어 법칙

```
wz = clamp(k_w * e_b, ±0.30 rad/s)
vx = clamp(k_v * e_r, ±0.05 m/s)
|e_b| > 0.20 rad 이면 vx = 0
```

초기 이득: `k_v = 1.0`, `k_w = 1.0`.

정지는 허용 범위의 절반(`stop_ratio = 0.5`) 안에 들어왔을 때 한다. P제어는 경계에 닿자마자 멈추므로, 허용 범위 그대로 쓰면 최종 오차가 경계(예: 0.020 m)에 걸려 노이즈에 따라 판정이 흔들린다.

### 2.3 완료 판정

오래된 프레임으로 완료를 판정하면 안 된다. 움직이는 동안 들어온 값이 허용 범위 안이어도 실제 위치는 이미 다를 수 있다.

1. 허용 범위 안이면 정지한다.
2. **정지 시각 이후 촬영된 프레임**만 사용한다 (`header.stamp` 비교).
3. 3프레임 연속 허용 범위 안이면 성공이다.
4. 벗어나면 제어를 재개한다.

구현 (`session.py`): 정지 명령 뒤 `settle` 0.1초가 지난 뒤 찍힌 프레임부터 세고, 같은 프레임을 두 번 세지 않는다. 측정 지연이 `max_age`(1초)를 넘으면 그 측정으로는 움직이지 않고 정지해서 기다린다.

### 2.4 지연이 클 때: 반복 보정

측정 지연이 약 1초를 넘으면 연속 제어 대신 아래를 반복한다. 지연은 메시지 `header.stamp`와 현재 sim time의 차이로 측정한다.

```
측정 → 0.5초 이동 → 정지 → 새 프레임 대기 → 측정
```

### 2.5 실패 처리

| 상황 | 동작 | 결과 코드 |
|---|---|---|
| 제한 시간 초과 | 정지 | `ALIGN_TIMEOUT` |
| 시작 시 물체 없음 | 정지 | `OBJECT_NOT_FOUND` |
| 정렬 중 물체 놓침 | 정지 후 대기, 복구 안 되면 실패 | `OBJECT_NOT_FOUND` |

물체 없음 판정은 `interfaces.md` 5.3을 따른다: score 0.5 이상인 목표 클래스 검출이 연속 N프레임(예: 10프레임) 동안 없으면 실패다.
구현에서는 "새 측정을 마지막으로 **받은** 시각"에서 `lost_timeout`(1초, 10 Hz 기준 10프레임)이 지나면 실패로 본다. 촬영 시각(stamp) 기준으로 하면 측정 지연만큼 항상 늦어 보여서 지연이 클 때 물체가 보이는데도 실패한다.

성공 시 `error_code`는 빈 문자열이다. 속도 명령 노드가 끝나거나 취소되면 반드시 0 속도를 발행한다.
노드 종료(Ctrl+C, SIGTERM) 때도 실행 중인 목표를 먼저 멈춘 뒤 0을 보낸다. Gazebo 차체는 마지막 명령을 계속 유지하므로 이 0이 없으면 계속 굴러간다.

IK 실패 후 재정렬은 상태머신이 `standoff_m`만 바꿔 Align을 다시 호출한다 (최대 2회, `interfaces.md` 5.2). D는 Goal의 값을 그대로 쓴다.

## 3. 인터페이스 제안

### 3.1 토픽

| 토픽 | 타입 | 방향 | 용도 |
|---|---|---|---|
| `/perception/detections` | `vision_msgs/msg/Detection2DArray` | 구독 | `results[0].hypothesis.class_id`, `results[0].hypothesis.score`, `bbox.center.position` (`interfaces.md` 3.2) |
| `/camera/depth/image_raw` | `sensor_msgs/msg/Image` | 구독 | 거리 `Z` |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | 구독 | 내부 파라미터 |
| `/servoing/cmd_vel` | `geometry_msgs/msg/Twist` | 발행 | 베이스 미세 정렬 속도 |

`/perception/target_pose`는 C의 3D 추정이 나오면 입력으로 바꿔 비교한다 (6장).

### 3.2 제어권

D는 `/servoing/cmd_vel`만 발행하고 `/cmd_vel`에 직접 발행하지 않는다. 상태머신(A)이 현재 단계에 맞는 명령만 `/cmd_vel`로 전달한다 (`interfaces.md` 5.0). 구현 방식은 A가 정한다.

### 3.3 Align 액션

```text
# Goal
string target_class
float64 standoff_m
float64 timeout_sec
---
# Result
bool success
string error_code
float64 final_range_error_m
float64 final_bearing_error_rad
---
# Feedback
bool target_visible
float64 range_error_m
float64 bearing_error_rad
```

허용 오차는 goal에 넣지 않고 5.1장 값을 파라미터로 관리한다.

### 3.4 전환 조건 후보 (`interfaces.md` 5.1)

- 방위 오차 0.05 rad 이하
- 거리 오차 0.02 m 이하
- 정지 후 촬영한 3프레임 연속 만족

이미지 중심 오차(px) 기준은 쓰지 않는다. 카메라가 베이스 중심축에 있지 않으면 물체가 화면 중앙에 있어도 베이스 기준 오차가 남기 때문이다. 수치는 후보이며 B의 작업 공간과 그리퍼 크기로 확정한다.

## 5. 수치 검증

`docs/visual_servoing_check.py`로 확인했다. 시작 오차 거리 ±0.15 m, 방위 ±0.35 rad, 시나리오별 200회, 카메라 노이즈 2 px / 5 mm, `k_v = k_w = 1`. 결과의 오차는 측정값이 아니라 실제 위치 기준 p95다.

| 지연 / 주기 | 단순 판정 | 정지 후 판정 (2.3) | 반복 보정 (2.4) |
|---|---|---|---|
| 0.2 s / 0.1 s | 100%, 9 mm, 0.018 rad | 100%, 18 mm, 0.040 rad | 100%, 10 mm, 0.025 rad |
| 0.5 s / 0.2 s | 100%, 8 mm, 0.025 rad | 100%, 8 mm, 0.029 rad | 100%, 14 mm, 0.035 rad |
| 1.0 s / 0.5 s | 100%, **40 mm, 0.175 rad** | 100%, 18 mm, 0.045 rad | 100%, 19 mm, 0.046 rad |
| 2.0 s / 1.0 s | 61%, **97 mm, 0.605 rad** | 3% | **100%**, 17 mm, 0.038 rad |
| 4.0 s / 2.0 s | 8% | 2% | 44% |

해석:

- 지연 0.5초까지는 연속 P제어로 충분하다.
- 지연 1초부터 단순 판정은 성공으로 보고해도 실제 오차가 허용 범위를 넘는다.
- 지연 2초에서는 반복 보정만 안정적이다.
- 지연 0.2초 기준 이득은 `k_v` 0.5~2, `k_w` 0.5~4 전부 수렴했다.

한계: 등속 unicycle 모델 계산이다. 바퀴 동역학, 미끄럼, 마찰, 오검출은 없다. Gazebo와 실제 YOLO로 다시 측정해야 한다. 초점거리와 standoff는 임시값이다.

### 5.1 ROS 모의 폐루프 검증 (Align 액션 서버, 2026-11-10)

`mock_align.launch.py` + `mock_trials`로 조건마다 20회. Align 목표를 보내고, 끝난 뒤 모의 차체의 **실제** 오차를 잰다.
시작 위치: 물체에서 `standoff_m`(0.25 m) + 0.15 m, Nav2 도착 오차를 흉내 내 위치 오차 반지름 0.13 m, yaw ±0.15 rad. 카메라 10 Hz, 제어 20 Hz.

| 조건 | 액션 성공 | 성공했는데 실제로는 허용 범위 밖 | 실제 \|e_r\| 평균 / 최대 | 실제 \|e_b\| 평균 / 최대 | 정렬 시간 평균 / 최대 |
|---|---|---|---|---|---|
| 지연 0, 노이즈 없음 | 20/20 | 0 | 9.3 / 9.7 mm | 0.006 / 0.024 rad | 5.4 / 8.3 s |
| 지연 0.5 s, 2 px, 5 mm | 20/20 | 0 | 2.7 / 5.7 mm | 0.002 / 0.005 rad | 6.5 / 9.2 s |
| 지연 0.8 s, 2 px, 5 mm | 20/20 | 0 | 7.7 / 10.3 mm | 0.006 / 0.012 rad | 7.4 / 10.1 s |

- 모든 조건에서 실제 오차가 허용 범위(20 mm, 0.05 rad) 안이고, "성공이라 보고했는데 실제로는 아닌" 경우가 없다. 정지 후 프레임 판정(2.3)이 지연 0.8 s에서도 동작한다.
- 노이즈가 없을 때 거리 오차가 약 9.5 mm로 몰리는 이유: 멀리서 다가오다가 정지 범위(허용 범위의 절반, 10 mm) 경계에 닿자마자 멈추기 때문이다. 허용 범위 안이라 문제는 없지만, 더 가운데로 모으려면 `stop_ratio`를 줄이거나 정지 직전 감속을 넣는다 (6.1 파라미터 스윕에서 확인).
- 경계 동작 확인: 잘못된 목표(빈 클래스, `standoff_m` 0, `timeout_sec` 음수)와 실행 중 두 번째 목표는 거부, 취소하면 마지막 명령 0 후 CANCELED, 없는 클래스는 1.0초 뒤 `OBJECT_NOT_FOUND`, 노드 종료 시 마지막 명령 0.
- 한계: 차체 모델은 등속 unicycle, 카메라 장착 위치·각도는 임시값, 오검출은 없다.

### 5.2 Gazebo 카메라 정렬 시험 (2026-11-15)

`sim_align.launch.py` + `mock_trials scene:=sim`으로 20회. 5.1과 같은 시작 조건.
Gazebo Fortress(화면 없이, ogre2)가 렌더링한 **실제 깊이 영상**(640×480, 수평 화각 60°)과 boundingbox 카메라의 **정답 박스**로 정렬한다. 대상은 feat/yolo `pin`과 같은 모양(지름 2 cm, 높이 5 cm).
차체는 바퀴 물리 없이 cmd_vel을 그대로 따르는 단순 모델, 카메라 위치·각도는 5.1과 같은 임시값이다. 시간은 시뮬레이션 시간(RTF 약 0.65).

| 조건 | 액션 성공 | 성공했는데 실제로는 허용 범위 밖 | 실제 \|e_r\| 평균 / 최대 | 실제 \|e_b\| 평균 / 최대 | 정렬 시간 평균 / 최대 |
|---|---|---|---|---|---|
| Gazebo 깊이 + 정답 박스 | 20/20 | 0 | 7.6 / 8.4 mm | 0.003 / 0.012 rad | 6.1 / 8.5 s |

- **깊이는 물체 앞면까지라 중심보다 반지름만큼 가깝게 나온다.** 처음 시험에서 보고 오차 6 mm, 실제 오차 16 mm로 pin 반지름(10 mm)만큼 차이가 났다. 측정점을 카메라 반대쪽으로 클래스별 반폭만큼 미는 보정을 넣은 뒤 보고·실제 차이가 0.3 mm 이하가 됐다 (이 고정값 보정은 5.3에서 원기둥 모델로 바꿈). 모의 입력(5.1)에는 이 효과가 없어서 Gazebo에서 처음 드러났다.
- 남은 것: 검출을 YOLO 결과로 바꾼 시험(`gt_detections:=false` + C 검출 노드), 바퀴 물리가 있는 팀 차체로 바꾼 시험. 실제 카메라 위치는 5.3에서 반영.

### 5.3 팀 관측 자세 카메라로 시험 (2026-11-22)

카메라 위치를 B의 관측 자세로 바꿔 5.2와 같은 방식(Gazebo 깊이 + 정답 박스)으로 시험했다 (`camera_pose:=near|pregrasp`).
카메라 TF는 feat/grasp(5741526) URDF에 관절값을 넣어 계산했다. near는 B 실측 TF와 1 mm 안으로 같다.

| 자세 | `base_link` 기준 카메라 x, z | 숙임각 | 화면에 들어오는 물체 거리 (pin 중심, 계산) |
|---|---|---|---|
| near | 0.260, 0.206 m | 57.9° | 약 0.30~0.59 m |
| pre-grasp (11/21, 69.3°) | 0.304, 0.150 m | 69.2° | 약 0.31~0.46 m |

**깊이 → 물체 중심: 고정 반폭 대신 원기둥 모델 (2.1).** 5.2의 고정 보정(pin 10 mm)은 옆에서 볼 때만 맞았다. pre-grasp처럼 위에서 보면 bbox 중심이 윗면에 닿아 보정이 너무 커져서, 보고 오차가 실제보다 0.35 m에서 4.6 mm, 0.32 m에서 9 mm 컸다. 원기둥 모델로 계산한 "맞는 보정량"(near 0.35 m 8.6 mm, pre-grasp 0.35 m 5.0 mm, 0.32 m 1.1 mm)이 관측값과 같아서, 이 모델로 중심축을 구하도록 바꿨다.

바꾼 뒤 결과 (각 10회, Nav2 도착 오차 반영: near는 시작 `standoff + 0.15` m ± 0.07 m, yaw ±0.15 rad / pre-grasp는 직전 near 정렬 끝에서 시작해 ± 0.02 m, ±0.05 rad):

| 자세, `standoff_m` | 액션 성공 | 실제 \|e_r\| 평균 / 최대 | 보고 − 실제 거리 오차 | 정렬 시간 평균 / 최대 |
|---|---|---|---|---|
| test(임시), 0.25 | 10/10 | 6.9 / 8.3 mm | 0.3 mm 이하 | 5.7 / 7.5 s |
| near, 0.35 | 10/10 | 6.9 / 7.9 mm | 0.5 mm 이하 | 5.3 / 6.6 s |
| pre-grasp, 0.35 | 10/10 | 7.0 / 7.9 mm | 0.3 mm 이하 | 3.5 / 3.8 s |
| pre-grasp, 0.32 | 10/10 | 6.8 / 8.3 mm | 0.3 mm 이하 | 2.8 / 3.1 s |

- 정답 박스는 화면 끝에 걸린 물체도 잘린 박스를 내므로, 화면 경계 근처(pre-grasp 0.32 m 이하, near 0.35 m 이하)에서 YOLO가 계속 잡는지는 이 시험으로 알 수 없다. C 측정(PR #3, 11/21)으로는 pre-grasp 0.30 m에서 부품이 화면 아래로 잘려 미검출, near 0.35 m에서 pin 점수 0.40(기준 0.5 미만)이다.

**같은 클래스 물체가 여러 개일 때.** 처음에는 매 프레임 점수가 가장 높은 박스를 골라서, 같은 클래스가 둘이면 정렬 중에 갈아탈 수 있었다. 첫 프레임은 `base_link` 방위가 가장 작은 검출(Nav2가 차체를 물체 쪽으로 세우므로), 이후는 직전 박스에 가장 가까운 검출을 따라가게 바꿨다 (`tracking.py`). 처음에 "화면 가운데에 가장 가까운 검출"로 했더니 카메라가 차체보다 0.26 m 앞에 있어 차체 정면과 달라서 방위 기준으로 바꿨다.

| 시험 (near, 0.35, 같은 pin을 목표 옆 0.18 m에 하나 더) | 목표 pin에 정렬 | 옆 pin에 정렬 |
|---|---|---|
| 20회 | 18 | 2 |

- 옆 pin에 정렬한 2회는 둘 다 Nav2 도착 오차 때문에 시작 시점에 옆 pin이 차체 정면에 더 가까웠다 (목표 방위 0.25 rad, 옆 pin -0.11 rad). 정렬 중 갈아탄 경우는 없다.
- 같은 클래스가 이 정도로 가까우면 클래스 이름만으로는 구분할 수 없다. 상태머신이 목표 물체의 예상 위치를 Align에 넘겨주거나(필드 추가), 같은 클래스 부품 사이 간격을 Nav2 도착 오차보다 충분히 크게 둬야 한다 (interfaces.md 6장 "같은 클래스 물체가 여러 개일 때").

### 5.4 YOLO 검출로 정렬 (2026-11-22)

5.3과 같은 조건에서 정답 박스 대신 C의 검출 노드(feat/yolo 71f6ed7 `yolo_detector.py`, PR #3 Drive 공유 640 모델, PyTorch, 점수 0.5 이상)로 정렬했다. 각 8회.

이 PC(Core Ultra 5 125H, WSL)에서는 추론이 프레임당 약 0.1~4 s로 들쭉날쭉해서(중앙값 약 0.4 s, 전원 '균형 조정'에서 1.2 GHz) 정렬 기준 3 Hz가 안 나온다. 그래서 Gazebo를 0.1배속(`rtf:=0.1`)으로 돌려 **검출 품질만** 봤다. 모든 노드가 시뮬레이션 시간을 쓰므로 시뮬레이션 시간 기준 검출 주기는 약 6~8 Hz다. 주기·지연 영향은 모의 시험(PR #3, 3 Hz 15/15)으로 따로 봤다.

| 목표, 자세, `standoff_m` | 액션 성공 | 실패 | 실제 \|e_r\| 최대 (성공) | 보고 − 실제 |
|---|---|---|---|---|
| pin, near, 0.40 | 2/8 | `OBJECT_NOT_FOUND` 6 | 2.4 mm | 0.5 mm 이하 |
| pin, near, 0.35 | 2/8 | `OBJECT_NOT_FOUND` 6 | 1.7 mm | 0.3 mm 이하 |
| pin, pre-grasp, 0.35 | 1/8 | `OBJECT_NOT_FOUND` 7 | 6.1 mm | 0.3 mm 이하 |
| block, near, 0.40 | 8/8 | 0 | 9.0 mm | 0.4 mm 이하 |
| block, pre-grasp, 0.35 | 8/8 | 0 | 7.7 mm | 0.3 mm 이하 |

- block은 프레임 대부분에서 검출돼(near 259장 중 253장) 전부 성공했다. 정렬 쪽(깊이·원기둥 보정·제어·완료 판정)은 YOLO 박스로도 정답 박스와 같은 정확도로 동작한다.
- pin 실패는 모두 검출이 1 s 넘게 끊긴 경우다. 이 모델은 near에서 0.45 m 이상 pin을 못 잡았고(conf 0.1에서도 없음), pre-grasp에서는 정렬 끝(0.35 m 근처)에서 놓쳤다. C가 말한 은색 pin 윗면 문제(PR #3, 11/21)와 같다. C의 4차 모델(pin 색 변경)로 다시 시험한다.
- 성공이라고 보고했는데 실제로는 허용 범위 밖인 경우는 없다 (검출이 끊기면 실패로 끝남).

## 6. 평가 계획

비교 대상:

1. 보정 없음 (Nav2 정차만)
2. 연속 P제어 + 정지 후 판정
3. 반복 보정
4. 입력 비교: 픽셀+깊이 직접 계산 vs `/perception/target_pose`

측정 항목: 최종 거리 오차, 최종 방위 오차, 정렬 시간, 성공률, 이후 파지 성공률. 조건별 같은 시작 위치를 반복한다.
